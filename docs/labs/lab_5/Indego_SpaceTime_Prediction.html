Space-Time Prediction of Bike Share Demand: Philadelphia Indego

Author

Ming Cao

Published

December 1, 2025

Introduction

The Rebalancing Challenge in Philadelphia

Philadelphia’s Indego bike share system faces the same operational challenge as every bike share system: rebalancing bikes to meet anticipated demand.

Imagine you’re an Indego operations manager at 6:00 AM on a Monday morning. You have: - 200 stations across Philadelphia - Limited trucks and staff for moving bikes - 2-3 hours before morning rush hour demand peaks - The question: Which stations will run out of bikes by 8:30 AM?

This lab will teach you to build predictive models that forecast bike share demand across space (different stations) and time (different hours) to help solve this operational problem.

Learning Objectives

By the end of this assignment, you will be able to:

  1. Understand panel data structure for space-time analysis
  2. Create temporal lag variables to capture demand persistence
  3. Build multiple predictive models with increasing complexity
  4. Validate models temporally (train on past, test on future)
  5. Analyze prediction errors in both space and time
  6. Engineer new features based on error patterns
  7. Critically evaluate when prediction errors matter most

Assignment Structure

Part 1 (In-Class/Together): Work through Q1 2025 data following this code

Part 2 (HW5 - Teams of 2): - Download a different quarter of Indego data (Q2, Q3, or Q4 2024) - Apply the same workflow to your quarter - Analyze error patterns in your quarter - Add 2-3 new features to improve the model - Write a brief report on what you learned

Create Time Bins

We need to aggregate trips into hourly intervals for our panel data structure.

Code 
indego <- indego %>%
  mutate(
    # Parse datetime
    start_datetime = mdy_hm(start_time),
    end_datetime = mdy_hm(end_time),
    
    # Create hourly bins
    interval60 = floor_date(start_datetime, unit = "hour"),
    
    # Extract time features
    week = week(interval60),
    month = month(interval60, label = TRUE),
    dotw = wday(interval60, label = TRUE),
    hour = hour(interval60),
    date = as.Date(interval60),
    
    # Create useful indicators
    weekend = ifelse(dotw %in% c("Sat", "Sun"), 1, 0),
    rush_hour = ifelse(hour %in% c(7, 8, 9, 16, 17, 18), 1, 0)
  )

We’ll spatially join census characteristics to each bike station.

# Create sf object for stations
stations_sf <- indego %>%
  distinct(start_station, start_lat, start_lon) %>%
  filter(!is.na(start_lat), !is.na(start_lon)) %>%
  st_as_sf(coords = c("start_lon", "start_lat"), crs = 4326)

# Spatial join to get census tract for each station
stations_census <- st_join(stations_sf, philly_census, left = TRUE) %>%
  st_drop_geometry()

# Look at the result - investigate whether all of the stations joined to census data -- according to the map above there are stations in non-residential tracts.

stations_for_map <- indego %>%

Create Temporal Lag Variables

The key innovation for space-time prediction: past demand predicts future demand.

Why Lags?

If there were 15 bike trips from Station A at 8:00 AM, there will probably be ~15 trips at 9:00 AM. We can use this temporal persistence to improve predictions.

Temporal Train/Test Split

CRITICAL: We must train on PAST data and test on FUTURE data!

Why Temporal Validation Matters

In real operations, at 6:00 AM on March 15, we need to predict demand for March 15-31. We have data from Jan 1 - March 14, but NOT from March 15-31 (it hasn’t happened yet!).

Wrong approach: Train on weeks 10-13, test on weeks 1-9 (predicting past from future!)

Correct approach: Train on weeks 1-9, test on weeks 10-13 (predicting future from past)

  1. Operational implications:

Based on the test-set results, the best-performing model achieves an MAE of approximately 0.61 trips per station-hour. Operationally, this level of error is fairly small: most Indego stations experience modest hourly demand, so being off by half a trip on average is reasonably good for system-wide forecasting. For routine morning and mid-day rebalancing decisions, this accuracy is likely “good enough,” especially when paired with human operator judgment.

However, prediction errors become more consequential during high-demand, peak-period windows, particularly the PM rush, where both absolute demand and model error increase. Misallocation during these periods could lead to stations running empty or full sooner than expected, which directly impacts riders’ ability to access bikes. Errors at high-demand stations in Center City and University City are especially operationally important because these stations act as hubs; small forecast mistakes can propagate quickly into system-wide shortages.

Overall, I would recommend deploying this forecasting system with human oversight, particularly during peak periods. The model performs well enough to guide general rebalancing strategy but should not be used as an autonomous decision-making tool. If adopted, Indego should monitor real-time usage and adjust rebalancing routes dynamically when predictions diverge from observed activity.

The demographic error analysis shows that prediction errors are not evenly distributed across Philadelphia. Specifically:

This uneven performance raises potential equity concerns. While these neighborhoods are not typically considered disadvantaged, unequal service reliability across demographic groups can still exacerbate perceived or actual inequities in mobility access.

To avoid unintentionally worsening disparities in bike availability, I recommend incorporating the following safeguards:

Error-aware rebalancing rules Stations with historically higher prediction errors should receive more conservative buffer stock (extra bikes or empty docks).

Continuous performance auditing across neighborhoods Track MAE by demographic characteristics to ensure no community consistently receives lower-quality forecasting.

Hybrid human + model operations Allow dispatchers to override model recommendations in areas where errors are known to be unstable.

Feature expansion focusing on equity Include POI, event schedules, and seasonal factors that may disproportionately affect certain communities.

A predictive model should not unintentionally drive inequitable operational decisions, so transparent monitoring is essential.

Assumptions that may not hold in real deployment

Station homogeneity: Fixed effects partially address differences across stations, but they assume constant station-specific behavior, which is not always realistic.

Linear relationships: Many relationships (e.g., between weather and demand) may be nonlinear, reducing model accuracy during extreme conditions.
